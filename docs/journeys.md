# Customer journeys

Status describes repository implementation, not hosted/provider acceptance. **Built** means the path exists; **partial** means a required connection or application step is absent; **missing** means no implementation. `web/` below means `apps/web/`; `api/` means `apps/api/`. `{org}` and `{customer}` are organization and Customer IDs.

## CRM relationship intake

CRM Dashboard is `/crm`. Contacts at `/crm/contacts` is one directory of people and companies (All, People, Companies, optional grouping by company); new contacts must be a Person or a Company, and existing records stay Unspecified until someone classifies them. Lifecycle and temperature are independent of type. Contact detail is `/crm/contacts/{contact}` and shows company affiliations or associated people. Pipeline at `/crm/pipeline` operates opportunities; opportunity detail is `/crm/opportunities/{opportunity}`. Tasks (`/crm/tasks`) and relationship stages (`/crm/contacts/stages`) are contextual, not sidebar destinations. Old `/sales`, `/customers`, `/opportunities` and `/follow-ups` links redirect temporarily (removal criteria in `docs/data.md`).

Contacts Import and Library Sources/file selections enter the same source, mapping, duplicate review, confirmation and report path at `/library/imports/new`. Worksheet mappings can retain one-way association; source Sync now refreshes the existing Library snapshot and opens reviewed CRM updates. Automatic CRM scheduling is not enabled. Removed source rows preserve the contact; conflicting local edits appear as failed import rows requiring reconciliation. Live Google/Microsoft authorization and provider access remain separate acceptance evidence.

## Staff-provisioned onboarding

| Step / route | Owner | Status and evidence |
| --- | --- | --- |
| `/platform/organizations`: Provision organization | Platform provisioning | **Built.** `web/features/platform/organizations/provision-form.tsx`; `provision_organization`. An optional starting setup is stored as a `provisioned` draft in the same transaction; nothing is applied. |
| Owner's first sign-in | Organization Setup / configuration | **Built.** As for sales-led onboarding: the draft opens for review, labelled "Prepared by GildOps", until applied, discarded or set aside. |

A business's setup can be read back out as a setup document (`readBusinessSetup`, backed by `read_business_setup`): kinds of work with stages and what each means, moves, steps, needs and online booking; fields; roles other than the founding one; opening hours; wording and menu order; who it serves; brand colour and lettering; customer forms started from a form template; "on an event, move the job" rules; and switched-on modules. It never reads customers, jobs, invoices, payments, prices, the public address or page text, the logo, phone numbers, payment accounts or connected apps. Platform staff holding `platform.catalogue` save a business as an unpublished starting template from its page under `/platform/organizations/{org}` (Save as template), and publish, unpublish or rename templates on `/platform/catalog` (Starting templates). Owners only ever see published templates.

Applying any setup draft is safe to repeat: every step finds what an earlier run made by name or key before creating anything. When an apply stops part-way the failed draft stays in history and the same document is offered again at once (`retry_configuration_proposal`); applying it finishes the setup with nothing made twice. Applying is not all-or-nothing. A template draft leaves out modules and features the plan does not include rather than failing.

## Business configuration

Both acquisition paths reach the same versioned business profile editor in Setup and Organization Settings → Words & navigation (`/settings/terminology`). It controls authored vocabulary, labels and the ordered workspace page labels. Missing configuration keeps neutral defaults without asserting that setup was completed. Permissions and entitlements always filter the chosen destinations. `/platform` has its own guarded shell; GildOps operating-organization Membership and exact live platform permissions remain required. Old organization Platform URLs render the organization not-found page.

## Work creation

Work Home, Work Items and Schedule open `/organizations/{org}/work/new` through the same action. The existing Work creation form, server action and database tenant/permission checks own the operation. `?type=` selects a type; `/work?create=1&type=...` redirects to the creation page. Missing types or starting stages show the prerequisite on the page; a member with `field.manage` adds the first type or the starting stage there (named by them, through the same actions and policies as Work type settings) and continues creating with the type kept, while others see what is missing and any type that is ready. Ready types expose customer, location, resource, optional asset and custom-field inputs. Errors retain the draft; default Work entry returns success and Cancel to Work Items. Finance's explicit `returnTo=quote` entry instead opens the newly created Work's Financials on success and returns Cancel to New quote. Dirty drafts guard links, type switches and browser unload through the shared unsaved-changes hook.

## Guided configuration and first-use recovery

Setup is a readiness view over canonical owners (ADR-039). A kind of work created in Work configuration starts with Booked, In progress and Done (Booked → In progress → Done, Booked → Done; Done counts as done and frees resources), which the owner may rename or delete. Operations names a missing starting stage as an optional gap and opens the first affected type's Workflow directly. An explicit tab remains selected; implicit zero-stage entry opens Workflow. Name and scheduling behavior save separately. Guided editor links carry `setupStep` and offer Return to setup with that step retained; saves invalidate readiness, and the next read reflects the saved records. Relationship stages are observed independently and never gate Work quotes. Scheduling resources and hours are shown only for scheduled work. Live organizations can review Setup without launching again; GildOps' operating Organization uses the same tenant permissions, readiness calculation and editor destinations.

New quote distinguishes a missing catalog, missing Work, unmatched search and a role restriction. Missing prices lead to Catalog & pricing and Return to new quote; missing Work leads to canonical New work, including its existing missing-type/stage recovery, then the created record's Financials. Nothing is named or created automatically. Platform providers, connector registrations, email-delivery evidence and runtime assignments retain their own privileged surfaces. Ready to connect is adapter/registration configuration evidence, not live authorization, synchronization or delivery verification.

## Dispatch and resource assignment

Dashboard attention links open `/organizations/{org}/work/dispatch` with the matching date and assignment filter. Dispatch uses one database-filtered queue beside a selected Work inspector; optional availability context reads the same projection as Schedule, and Map retains coordinate behavior. Upcoming means the seven local dates after the selected day in both places. Assign resources changes participants without changing time; Schedule/Reschedule checks feasibility without writing, then commits through the existing scheduling command. Focused dialogs protect unsaved changes and retain refused input. Schedule remains the full Day/Week/Month visual calendar, linked with date/resource context. Required staffing is distinguished from assessed time availability.

## Organization Home

`/organizations/{org}/home` gives a cross-workspace overview using existing authorized source projections. Exact overview figures lead attention, distinct personal responsibilities, other dated obligations, relevant business performance and recent activity. Work exceptions open Dispatch with date and selection/filter context; invoices open Finance's existing inspector; CRM responsibilities open the selected task. Today and Upcoming are disjoint in Home, with continuing Work kept under Today and all seven subsequent local dates included in Upcoming. Attention and reporting controls preserve their own URL state. Quick actions and the existing command palette/Agent remain shared; New work opens the canonical `/work/new` route. Optional performance/activity selections stay in browser storage with explicit save-failure feedback. Source failures omit unknown figures while healthy workspaces remain readable.

## Gaps

- Telephony provisioning is manual; neither onboarding path provisions a carrier binding/number.
- Accepted configuration is recorded at handoff, not automatically applied to the new business. An agreed starting template becomes a draft the owner applies, but no screen yet records a template on a proposal (ADR-051 retired the platform-plan proposal builder).
- Who a business serves (`organization_identity.serves`: people, companies or both) is stored and set from Business information or a setup, but nothing yet changes behaviour on it. A portal link belongs to one contact, so several people at one company cannot each have their own portal access.
- A setup read back leaves out what the setup document cannot describe: individually switched-off features, prices (in the source business's currency), booking price and intake form, customer forms built from scratch, rules other than "on an event, move the job", the public page and logo.
- Hosted routing, browser receiving, external voice sessions and carrier transfers still require deployed configuration and real provider acceptance. Local tests do not establish live readiness.
- Self-serve and sales-led onboarding share Setup but do not reconcile their founding and commercial inputs through one onboarding contract.
