# 24. Guiding Principle

The system should follow:

**80% Platform + 15% Configuration + 5% Custom Development**

rather than:

**100% Custom Application**

The goal is that when a business says:

> "We do things differently."

your first response isn't:

> "We need to rebuild the application."

It is:

> "Which entity, workflow, rule, module, or integration represents that difference?"

If the answer is configuration, configure it.

If it is a reusable capability, turn it into a module.

Only when it is genuinely unique should it become custom development.

The interesting part is that this also fits the **workspace architecture** we discussed previously: organization → workspace/project → entities → workflows → agents → integrations, with the AI layer sitting over the operational data rather than being its own disconnected feature.

I would take this one step further architecturally: make **"Business Template"** a first-class object. Then you could have templates like `Field Service`, `Equipment Maintenance`, `E-commerce`, `Professional Services`, `Property Management`, etc., and when you onboard a company you **clone a template and customize it** rather than starting from zero. That is what turns your previous four apps into the beginnings of an actual product platform.

# 2. Don't charge primarily per user

This is important.

If you're selling a generic CRM, per-seat pricing makes sense.

But if you're replacing several operational systems for a 15-person company, charging:

> $20 × 15 users = $300/month

is probably leaving enormous money on the table.

The business isn't buying "15 accounts."

They're buying:

* fewer administrative hours
* fewer missed jobs
* better dispatching
* faster customer response
* better utilization
* better reporting
* automated follow-up
* fewer mistakes
* potentially more sales

So I'd use:

### Platform fee + modules + usage + implementation

Something like:

| Component          |        Example |
| ------------------ | -------------: |
| Platform           |    $199–499/mo |
| Operations modules |    $100–500/mo |
| AI                 | $100–1,000+/mo |
| Voice/dialer       |    usage-based |
| Integrations       |     $25–200/mo |
| Custom development |    project fee |
| Implementation     | $1,500–15,000+ |
| Enterprise         |         custom |

Those aren't rigid market prices; they're a starting framework. Current B2B SaaS benchmarks put SMB products roughly around $100–500/month and vertical SaaS around $199–599/month, while higher-touch/mid-market products move into the thousands per month. ([SaaSPriceLab][1])

Your advantage is that you're not limited to the normal SaaS pricing ceiling because **implementation + customization + automation** are part of the offer.

# 9. Multi-tenancy

This is absolutely foundational.

Suppose:

```text
tenant A = landscaping company
tenant B = equipment company
tenant C = sales company
```

They all use the same database.

But:

```text
tenant A
   ↓
customers WHERE tenant_id = A
```

while:

```text
tenant B
   ↓
customers WHERE tenant_id = B
```

Supabase's Row Level Security is particularly useful here. RLS policies operate at the Postgres level and can effectively impose a tenant-aware `WHERE` condition on queries. ([Supabase][3])

Supabase Auth issues JWTs and integrates with RLS, so authentication and database authorization can work together. ([Supabase][4])

I would make this a hard architectural rule:

> **Every tenant-owned table has `tenant_id`, and every tenant-owned table has RLS.**
