# Communications surfaces

Workspace and feature surface specifications. System-wide rules, including **Core rules**, are in [docs/ui-system.md](../ui-system.md). Before changing a surface here, check `docs/decisions/` for ADRs that name it.

## Communications Home

Communications Home at `/comms` is the workspace Dashboard, with Communications retained in its page location. It leads with exact operational counts (missed calls for the selected organization-timezone period; outstanding wrap-up, unread and unassigned conversations), attention, conversation and call previews, recent activity and selected-period call performance. An implicit attention selection chooses the first nonempty category; explicit URL selections persist. Setup is not an attention category. One calling-readiness line uses the same application projection as Dialer: platform unavailability has no tenant setup action, while an organization-owned number-assignment gap links only through an eligible configuration door. Organization Setup remains the onboarding owner. Empty regions stay compact without empty table headings. Conversation previews retain channel, ownership, unread state and canonical destinations; legacy queue/channel/search URLs retain their filtering and link context. Previews stay bounded and never replace exact totals. Call performance labels the answer rate and its denominator; no recorded calls or an incompatible search leaves the rate unknown. Recent activity uses dated timestamps rather than repeating a Today feed. No presence, schedule, delivery or provider readiness is invented.

## Conversations

The operator destination is named Conversations; existing `/comms/inbox` routes and channel-specific conversation records remain canonical. Its toolbar has one row of All, Mine, Unassigned and Unread views, plus separate channel and lifecycle selectors. Search and independent filters remain URL-backed through client navigation, including when opening a conversation or changing a filter. The list reads a tenant-scoped feed of SMS and email conversations and website chat threads. Website chat retains its own thread, claim state and route; its read state is unknown and never counted as unread. Feed pages use a stable timestamp, source and ID cursor, so equal-time rows are not lost or repeated. Loading, an empty result and a refused or failed read are distinct; failed reads offer retry and never claim zero work. Slow results and pagination from an earlier filter cannot overwrite the current view. The list and selected conversation split according to available container width; narrow containers show the selected pane with a return control. Empty lists do not reserve a large unused detail pane. A selected email or SMS conversation offers Call when the contact has an eligible number and the member may place calls. Its contact context and recent calls appear in a side panel at wide container widths and the shared drawer at narrow widths; linked Support cases are disclosed on demand. New message remains explicit; sending readiness and permissions remain enforced by the existing channel commands. A contact-wide merged thread is not yet offered: separate channel records remain distinct.

## Dialer

Dialer uses `/calls` as an A11 console (`features/communications/voice/dialer-workspace.tsx`). `PageLocation` publishes Communications / Dialer; the content retains one semantic h1. One toolbar groups Standard/Focus modes on the left and Pop out dialer, Call history and Calling settings actions on the right. Call list and Contact are pressed visibility buttons, not navigation tabs. The Call list shows open Call tasks (`domain-model.md`, Task and Follow-up), earliest due first. Its All call tasks link opens Tasks filtered to open calls and is omitted for an empty list; the empty list says no contacts have been added and links to Contacts. Members who may manage tasks get Add to list (in the list header, and in the empty list): one fixed-size dialog in three steps, Contacts, Call details and Review. Contacts searches the directory and keeps several choices across searches, showing each phone number and whether the person is already on the list; someone already on the list or with no phone number cannot be chosen, and Next needs at least one choice. Members who may add contacts (`customer.create`) can Create contact inside the dialog through the canonical creation form; the new contact is chosen when they can be called. Open Contacts is always offered. Call details requires a Reason for calling (nothing is filled in on the person's behalf) and keeps Due (organization timezone), Owner and Note; Back keeps every choice and detail. Review reads the chosen contacts again and shows who will be added, who is already on the list and who has no phone number, with the reason, due date and owner; only those still eligible are added, each as one open Call task. The database holds one open Call task per contact, so simultaneous adds never create a second entry; someone another person added meanwhile is reported, not added twice. Success is a toast; when anyone chosen was not added, the dialog lists each contact's result. Contacts and a contact's own page offer the same through Add to → Call list (`crm.md`), with the same required reason. Every way in is shown only when the business has the Dialer and Tasks and the member may manage tasks and view contacts (`customer.read`; choosing who to call is browsing contacts), and every write checks the same. The list itself shows each entry's name and number to anyone who places calls, through the Dialer's own narrow read of contacts on the list (`security.md`), so a caller without `customer.read` still works the list but cannot browse the directory. Members holding `call_list.remove` get Remove from list in each entry's actions menu: it asks first, then cancels that open Call task. The contact, their completed calls, notes and history, and any call in progress are left as they are, and they can be added again. Managing tasks does not include removal: cancelling an open Call task, or changing its kind, needs `call_list.remove` wherever it is attempted, and the Tasks screen offers Cancel on Call tasks only to members who hold it. No import or synchronized-sheet route onto the list is offered. Archived contacts are never added. One open Call task per contact is the rule; several independently scheduled calls to one contact are a later decision, not a separate queue. The list and its controls never say follow-up or queue. Pop-out is an action through the existing organization telephone; it transfers the number, chosen caller line and matching customer attribution, and returns the edited draft without attaching an unrelated number to the selected customer. The global telephone utility remains available. Configuration retains its canonical Communications destination. At 64rem of actual console width, the call list, central calling console and customer context form a three-column composition that follows its content height up to the available viewport height, with independent scrolling for long regions. Empty side regions stay at their natural height and use compact text rather than tall centred empty-state illustrations. Number entry and the keypad share a row once their own form has 26rem available; narrower forms keep a compact keypad below. Sidebar and Agent/page-panel width therefore affect composition without requiring a viewport resize. Below that width a Call list / Calling / Contact switch selects one mounted region; live calls expose Show call controls when another region is selected. Focus keeps only calling and workflow; Call history returns to Standard before opening its anchor. The central console has one compact readiness line, bounded number entry/dial pad or live controls, and a Call task region only when a task is selected. A disabled Call control references its visible blocker; idle browser registration says Connects when needed rather than presenting a failure. Needs wrap-up appears only when recorded calls await outcomes. The Contact region owns identity and recent calls; Call task owns reason, due date, owner and notes. An unselected desktop Contact region does not reserve a third column; it remains reachable in the narrow-screen region selector. Empty side regions retain truthful context. The history disclosure owns its heading, compact daily summary metrics, URL-backed filters, results and pagination in that order; `#call-history` and count/link semantics are preserved. No transcript, recording, script or fullscreen controls are offered without a source. The development-only `/dev/dialer` fixture uses the real shell with a simulated telephone for live-call layout checks; it is not provider evidence. Calling and messaging permissions, readiness and guarded commands remain unchanged.

## Channel diagnostics

Channel diagnostics reuse `messagingSenders` and the existing sender/provider facts. The UI distinguishes planned/unentitled/disabled features, missing provider/callback/relay configuration, inactive or non-SMS numbers, missing active identities, and unverified sending domains. Sender configuration does not grant `message.send`; configuration checks passing never asserts provider acceptance or delivery. Outbound email and mailbox synchronization remain separate capabilities.
